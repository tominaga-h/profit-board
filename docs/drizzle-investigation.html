Q1. コードはシンプルになるか 結論: ほぼ同じ

判定
差し引きゼロ
クエリは短くなるが、schema ファイル・drizzle.config.ts・drizzle client の初期投資が上乗せ

短くなる部分（減るコード）

現状

Supabase PostgREST チェーン

const { data, error } = await supabase
  .from('m_users')
  .select('*')
  .order('id')
Drizzle

クエリビルダ

const data = await db
  .select()
  .from(mUsers)
  .orderBy(mUsers.id)

特に効くポイント

  • トランザクション: composables/useMembers.ts の DELETE→UPDATE→INSERT を db.transaction() で 1 本化
  • 関連たどるクエリ: select('*, m_projects(*)') → db.query...findFirst({ with: { project: true } })
  • PostgREST 固有 API: .select('id', { head: true, count: 'exact' }) などの「DSL の細部」を覚えなくてよくなる

増える部分（コスト）

増えるもの影響度備考
db/schema/*.ts（schema-first なので必須） 中 SQL migration を書き写す工数。or drizzle-kit introspect で逆生成
drizzle.config.ts + DB クライアント 中 Supabase の Transaction mode プール / Direct 接続の選択が必要
型と schema の drift 検知 CI 小 database.types.ts 廃止した場合のみ
drizzle-zod の導入判断 小 後述の Q3 で詳述
⚠️
「コードが短くなる」は半分だけ本当 useFiscalYears のような単一テーブル CRUD では効果が小さい。
一方 usePerformance のように複数テーブル跨ぎ・集計がある場合は明確に読みやすくなる。

Q2. 拡張に耐えられるアーキテクチャか 結論: 上がる

判定
明確に上がる
トランザクション・JOIN・集計・型共進化。ただし「DB だけ Drizzle」のハイブリッド運用が前提

耐える点（Pros）

Pros
  • 本物のトランザクション
    Postgres 側の関数に閉じずアプリ側で原子化
  • JOIN・集計の表現力
    useDashboard, useProjectYears の N+1 パターンを集約
  • 型が schema と共進化
    push だけで型が追従。SQL 書く人と TS 読む人の分業が薄れる
  • テナント分離の差し込み口
    where 句を一箇所に集約できる下地ができる
Cons / 注意点
  • Supabase Auth は温存必須
    RLS をアプリ層に書き写すと弱くなる
  • Realtime / Storage は併用
    「データ取得=Drizzle、認証=Supabase、ファイル=Supabase」の使い分けルールが要る
  • DB が 2 系統になるリスク
    半分だけ置き換えると telemetry / RLS / 型が二重化して最も負債が残る形に

導入後のアーキテクチャ図（ハイブリッド）

図2: Drizzle 導入後のハイブリッド構成。DB I/O だけ Drizzle に置き換え、Auth/RLS はそのまま温存。

拡張性を左右する 3 つの軸

拡張シナリオDrizzle による改善条件
複数ユーザーが同時編集するトランザクション要件 大きく改善 db.transaction() が手に入る
集計クエリの増加（ダッシュボード・レポート） 大きく改善 SQL ビルダの表現力で集約
テナント分離 / RBAC の追加 条件付き RLS を温存し、アプリ層の where 句と二重化する必要あり
テナント分離で RLS を捨てたい場合 推奨しない 権限境界が弱くなる

Q3. Zod スキーマは不要になるか 結論: 不要にならない

判定
無くならない
Drizzle は UX 向け整形メッセージを生成しない。drizzle-zod で骨格は作れるが、手書き部分は残る

Drizzle が提供できる範囲

drizzle-zod の createInsertSchema(table) は DB カラムの NULL/必須・長さ上限・型 を Zod に写すだけです。

手書き Zod (現状)

member.ts より抜粋

export const memberRowSchema = z.object({
  family_name: z.string()
    .trim()
    .min(1, '姓を入力してください')
    .max(50, '姓は50文字以内で入力してください'),
  unit_price: z.number({
    invalid_type_error: '単価を入力してください'
  })
  .int('単価は整数で入力してください')
  .min(0, '単価は0以上で入力してください')
})
drizzle-zod (骨格のみ)

骨格は自動生成できる

export const memberRowSchema =
  createInsertSchema(mUsers, {
    family_name: // ここで上書き
      z.string().trim().email(...),
    unit_price: // ここで上書き
      z.number().int().min(0),
  })

drizzle-zod が「作れない」重要なルール

ルール由来drizzle-zod で生成
.trim() による値変換 UX 要件（前後の空白を保存しない） ×
.int()（NUMERIC(12,0) の事前警告） UX 要件（DB の暗黙丸めを前段で止める） ×
.refine()（稼働時間小数第2位チェック） UX 要件（浮動小数誤差を回避した桁チェック） ×
invalid_type_error: '金額を入力してください' UX 要件（空欄 → NaN を日本語で） ×
プロジェクト編集の重複検知（service_name × company_name） UX 要件（DB に UNIQUE 制約が無い） ×
🚫
「Drizzle を入れたら Zod が要らなくなる」は誤解 Drizzle は「型とクエリ」の道具。「ユーザー向けの整形済みメッセージ」「空欄時の日本語エラー」「DB 制約の前段の親切バリデーション」は別の関心事です。drizzle-zod は DDL→Zod の自動変換器であって、仕様→Zod の置き換えではありません。

現実的な 3 つの選択肢

案Zod の残り方向いている状況
A. Zod をそのまま残す lib/schemas/*.ts を手書き維持 現実解。drizzle-zod は土台に留め、refine と日本語メッセージは手書き
B. drizzle-zod で骨格、上書き createInsertSchema(table, { ... }) DDL と Zod の二重管理を 1 箇所に集約したい場合
C. Zod を捨てる Drizzle schema のみ。Postgres エラーを自前翻訳 推奨しない。error.code === '23503' 分岐が増殖する

推奨判断と意思決定フロー Recommendation

✅
推奨: 「DB I/O だけ Drizzle、Auth/RLS は Supabase」のハイブリッド構成 今すぐ全面移行は不要。1 composable だけプロトタイプ化して費用対効果を測るのが最良の次の一手です。

意思決定フローチャート

↑ ↑ ↑
Q: 両方とも増えない → 現状維持で十分

導入を止めるべき赤信号

  • RLS をアプリ層に書き写す羽目になる → Supabase の旨味が消えるので一旦停止
  • PostgREST 固有の count クエリ多用箇所の書き換えコストが見合わない → CRUD 単純箇所だけ Drizzle、集計は PostgREST のまま、という折衷案
  • 「Drizzle に置き換えたら Zod も要らなくなる」と誤解したまま進める → UX メッセージが消えてユーザー体験が劣化

段階的導入プラン Roadmap

全面移行ではなく、最小コストで投資判断材料を得るステップ構成です。

Step 0 · 採否決定

拡張要件の棚卸し

「複数テーブル集計」「同時編集トランザクション」が 12 ヶ月以内に発生するか確認。発生しないなら現状維持で十分。

Step 1 · 依存追加

drizzle-orm / drizzle-kit / drizzle-zod を導入

drizzle.config.ts に Supabase Postgres 接続情報と JWT の扱いを集約。service_role は使わず、PostgREST と同じ RLS を期待するなら anon + JWT を毎リクエストで渡す設計。

Step 2 · schema 逆生成

db/schema/*.ts を drizzle-kit introspect で生成

types/database.types.ts の依存箇所を import type { MUser } from '~/db/schema' に置換。CI で drift 検知を回す。

Step 3 · プロトタイプ

useFiscalYears を 1 個だけ Drizzle で書き直す

最も単純な 1 テーブル composable を 1 つだけ移行し、トランザクション・型・RLS の通り方を確認。全置換を一括でやらない。

Step 4 · 効果測定

useMembers.saveMembers を db.transaction に置換

DELETE→UPDATE→INSERT の「失敗時 false を返して再取得」パターンが tx.rollback() で集約できるか確認。これがうまくいけば拡張性メリットが確定。

Step 5 · 残置判定

Zod を残す方針を確定

drizzle-zod を骨格に採用し、refine() と日本語メッセージは lib/schemas/*.ts に集約。Postgres エラー翻訳は引き続き error.code 分岐で扱う。

Step 6 · 段階移行

残 composable を優先度順に置換

優先度: (1) 集計・トランザクション箇所 → (2) 単純 CRUD 箇所。Realtime / Storage / Auth はそのまま Supabase クライアントを継続利用。

完了基準（Definition of Done）

  • ✅ Supabase Auth / RLS が壊れていない（既存の middleware/auth.global.ts が AUTHORIZED を返す）
  • ✅ useFiscalYears の Drizzle 実装で RLS が効く（m_users に未登録ユーザーから 0 件）
  • ✅ useMembers.saveMembers で DELETE→UPDATE→INSERT が原子化される
  • ✅ 既存の Vitest テストが緑のまま（schema 周りはそのまま）
  • ✅ npm run dev / npm run build / npm run generate すべて通る
